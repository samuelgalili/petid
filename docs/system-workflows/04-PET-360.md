# 04 — Pet 360

Status of the concept as a whole: **`MISSING`**. What exists is a 57-column
`pets` row plus four satellite tables. There is no aggregate view, no fact
store, no timeline, and no provenance. This document says what is there, what
is not, and what the target model should be.

## Universal core + species extensions (PROPOSED)

Nothing below exists. It is the target shape, chosen so it fits the current
schema rather than replacing it.

```
                     ┌──────────────────┐
                     │       pets       │  ← stays as the identity row
                     │  (id, user_id,   │
                     │   name, type…)   │
                     └────────┬─────────┘
                              │ 1:N
                     ┌────────▼─────────┐
                     │    pet_facts     │  ← the new spine
                     ├──────────────────┤
                     │ pet_id           │
                     │ namespace        │  physical | health | nutrition |
                     │ key              │  behavior | preference | activity
                     │ value  (jsonb)   │
                     │ unit             │
                     │ source           │  USER_PROVIDED | VET_CONFIRMED |
                     │ source_id        │  VET_DOCUMENT | SYSTEM_DERIVED |
                     │ confidence       │  ACTIVITY_DERIVED | PURCHASE_DERIVED |
                     │ verification_    │  AI_INFERRED
                     │   status         │
                     │ observed_at      │
                     │ effective_from   │
                     │ effective_to     │  ← null = current
                     │ created_at       │
                     │ updated_at       │
                     └──────────────────┘
```

Why one table and not thirty: every fact needs the same eight provenance
columns, and the set of keys will keep growing per species. A key registry
(`pet_fact_definitions`: key, species applicability, data type, unit, privacy
class, whether medical) keeps it from becoming a junk drawer.

**Species applicability** lives in the registry, not in separate tables — which
answers "do not force dog-centric assumptions" without four parallel schemas:

| Namespace | dog | cat | bird | rodent |
|---|---|---|---|---|
| `physical.weight` | ✓ | ✓ | ✓ | ✓ |
| `physical.wingspan` | | | ✓ | |
| `physical.dental_condition` | ✓ | ✓ | | ✓ |
| `behavior.reactivity_to_dogs` | ✓ | | | |
| `behavior.scratching` | | ✓ | | |
| `behavior.vocalisation` | | | ✓ | |
| `nutrition.grit_provided` | | | ✓ | |
| `activity.walks_per_day` | ✓ | | | |
| `activity.enrichment_minutes` | | ✓ | ✓ | ✓ |
| `health.rabies_vaccination` | ✓ (legally required in IL) | ✓ | | |

See `27-SPECIES-DIFFERENCES.md` for the full split.

### Migration path from `pets`
`pets` keeps identity. Everything with a history — weight, mood, conditions,
food — moves to `pet_facts` with the current value mirrored back onto `pets`
for read speed. `age` stops being stored. `size` becomes derived. This is
additive; no existing column has to be dropped on day one.

## Pet 360 read model (PROPOSED)

A `GET /api/me/pets/:id/profile-360` that composes:

```
pets (identity)
  + latest pet_facts per key, with source and confidence
  + pet_vaccinations, pet_vet_visits (already exist)
  + pet_documents (+ extracted facts, once 06 exists)
  + orders joined by pet_id (needs the column)
  + activity aggregates (needs 08)
  + social counts (exists)
  + timeline (needs 18 consumed)
```

It must return provenance with every value. A client that cannot tell an
AI guess from a vet's number will present them identically, which is the
specific failure `05-PET-KNOWLEDGE.md` exists to prevent.
