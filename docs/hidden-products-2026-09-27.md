## What the shop, search and sitemap filter on

- Shop listing: `GET /api/products` reads `business_products`. A public caller does not receive a row whose `shop_hidden` is true. The browser still drops `in_stock === false` after that. `in_stock` is stock, and it is not how these products are hidden.
- Product search: the shop searches that same public list (`searchCatalogDetailed`). The assistant's catalogue search (`buildCatalogSearch`) also requires `coalesce(p.shop_hidden, false) = false` and `coalesce(p.in_stock, true) = true`.
- Category pages: `GET /api/categories` lists categories with `is_active`. Products in a category are the public `GET /api/products` list, optionally `?category_id=` or `?category=`, after the hidden rows are removed. A hidden product is not in that list.
- Sitemap: `public/sitemap.xml` lists marketing routes and no product URLs. `productSitemapPaths` is the only builder of `/product/<id>` entries, and it omits hidden products.
- Direct product URL: `GET /api/products/:id` answers 404 for a public caller when `shop_hidden` is true. The product page already renders that as "המוצר לא נמצא".
- The new catalogue `GET /api/catalog` is a different table. The shop does not read it. Its gate is `publication_state = 'PUBLISHED'` plus an eligible seller, an active priced offer and an approved image.

`shop_hidden` defaults to false. Admin sessions with a full view of the row still receive it, so the admin catalogue can see what was hidden. Shopper screens use the public list.

## How a cart behaves

A line is shown as "המוצר אינו זמין כרגע" and left out of the subtotal, the shipping threshold and the order payload only when a successful storefront response lists other products and not this one. An empty catalogue, a failed lookup, or a lookup that is still loading does not block checkout. If a client still posts a hidden id, `POST /api/orders` refuses that order with "המוצר אינו זמין לרכישה. אפשר להמשיך עם שאר הפריטים בעגלה." and writes nothing. The order total is still the sum of the lines the server resolved. The Cardcom webhook is unchanged and settles that total.

## How to hide, and how to restore

Workflow name: **Hide broken external product images**

File: `.github/workflows/production-hide-broken-image-products.yml`

Run it from branch `aws-migration` after this change is deployed, so migration `0061_product_shop_visibility.sql` is applied. In Run workflow, set "Use workflow from" to `aws-migration`, not `main`.

| step | input `mode` | input `confirmation` | writes? |
| --- | --- | --- | --- |
| dry-run | `dry-run` | leave empty | no |
| hide | `hide` | `HIDE-BROKEN-IMAGES` | yes |
| unhide | `unhide` | `UNHIDE-BROKEN-IMAGES` | yes |

Dry-run is the default. It prints, for each id, the current `shop_hidden`, the current `in_stock`, and the recorded previous value if a hold exists.

`hide` is a production data change. It needs the owner's approval before anyone runs it. The confirmation text is checked before anything connects, and a backup is taken before the write. `hide` inserts `product_shop_visibility_holds.previous_shop_hidden` with the value it found (false for a product that was on the shelf) and sets `shop_hidden` to true. Running it again does not overwrite that recorded value.

`unhide` sets `shop_hidden` back to `previous_shop_hidden` on that hold, then deletes the hold. It does not assume the product was visible. A hidden row with no recorded previous value is refused, and nothing is written. The append-only log `product_shop_visibility_events` keeps both the value before the action and the value after it.

Dry-run prints `allowlist_count=28`, then `ids:`, then the 28 ids in the same order as the tables above, then one detail line per id. Compare that list to this document before a write.

Both writes refuse any id that is not in either table above. Neither statement updates `in_stock`, price, variants, offers or inventory.
